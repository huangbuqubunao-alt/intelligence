# ADR-001：以任务和 Worktree 为单位的多 Agent 开发模式

## 状态

Accepted

## 日期

2026-07-14

## 背景

项目计划同时使用当前主控 Codex 对话、多个 Codex CLI 会话和多个 Grok Build 会话。如果所有会话长期按角色存在并共享同一工作目录，会出现：

- 不同 Agent 同时改写相同文件和本地状态。
- 分支、任务、聊天和检查证据无法一一对应。
- 长期角色对话积累过期上下文。
- 实现者自我验收，缺少独立证据。
- 产品决策停留在聊天中，其他 Agent 无法读取。

## 决策

采用以下开发运行模型：

1. 当前长期对话作为产品/项目主控，只负责规划、决策、分配和最终验收。
2. 独立任务是并行和上下文生命周期单位；角色只是会话提示配置。
3. 每张写入型任务使用独立 Git worktree、独立分支和一个主要实现会话。
4. 实现者与 Reviewer 优先使用不同模型；Reviewer 不修改业务代码。
5. 公共任务状态只由主控对话在主线维护。
6. 仓库文档、commit、Diff 和检查结果是共享事实；聊天决定必须写回仓库。
7. 默认 WIP 限制为两个写入任务和一个 Reviewer。
8. 所有实现必须经过实现、独立审查、主控验收、整合后检查四个阶段。

## 考虑过的替代方案

### 多个长期角色窗口共享同一 checkout

- 优点：启动简单，不需要管理 worktree。
- 缺点：文件冲突、状态污染、职责不清和 Diff 混杂。
- 结论：拒绝用于并行写入；只允许同一工作区中顺序执行实现和只读审查。

### 由一个主 Agent 自动生成所有代码

- 优点：协调成本最低。
- 缺点：上下文噪声大、缺少独立审查、长链路失败难定位。
- 结论：可用于单个小任务，不适合整个 MVP。

### 两个模型同时实现同一任务

- 优点：可比较方案。
- 缺点：成本翻倍、整合困难、责任边界模糊。
- 结论：只用于明确的短期技术选型实验；正式任务只保留一个实现者。

## 后果

- 需要先建立 Git 基线才能启动并行 worktree。
- 每张任务会多一个交接和审查步骤，但失败更容易定位和回退。
- 主控对话成为任务状态的唯一写入者，避免并行分支修改公共看板。
- 每个 worktree 需要独立本地数据、缓存、端口和测试 Vault。
- 实际并发受到人工审查与整合能力限制，而不是终端数量。
